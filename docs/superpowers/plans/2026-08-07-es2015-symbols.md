# ES2015 Symbols Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the ES2015 Symbol primitive, its wrapper and registry,
symbol property keys, symbol-aware reflection, and the well-known symbols.

**Architecture:** Guest symbols are host `symbol` primitives; well-known
symbols and the global registry are agent-level singletons in
`src/runtime/symbol.js`; `%Symbol%`/`%SymbolPrototype%` are per-realm. See
`docs/superpowers/specs/2026-08-07-es2015-symbols-design.md`.

**Tech Stack:** Plain ES2020 JavaScript with JSDoc types, the portable test
harness in `test/harness/`, pinned Test262 at
`b363f29d3c43c626dc852744ad64a0b48a003693`.

## Global Constraints

- Nothing under `src/` may import a host module; guest behaviour may not lean
  on host `eval`, `Function`, or host objects.
- The engine must not reuse the host's own well-known symbols (`Symbol.iterator`
  and friends); it mints its own with `Symbol(description)`.
- Well-known symbols and the `GlobalSymbolRegistry` are shared by all realms
  (ECMA-262 §6.1.5.1, §19.4.2.1). `Symbol`, `Symbol.prototype`, and wrapper
  objects are per-realm.
- ES5.1 string-key behaviour must not change: `for-in`, `Object.keys`, and
  `Object.getOwnPropertyNames` stay string-only, and own-key insertion order
  is unchanged.
- Built-in function `length`/`name` keep their ES5.1 attributes
  (`configurable: false`); ES2015's `configurable: true` belongs to issue #38.
- Every new portable suite must be registered in `test/suites.js`.
- Run `npx prettier --write` on every file touched before committing.

### Task 6: Prefix-scoped Test262 feature claims

**Files:**

- Modify: `tools/test262/es5-selection.js`
- Modify: `tools/test262/es5-selection.json`
- Modify: `tools/test262/upstream-select.js`
- Modify: `tools/test262/features.json`
- Modify: `test/es5-selection.test.js`

**Why:** the selection policy currently drops _every_ test that declares a
`features:` tag, so no Symbol test can ever be selected. A blanket claim would
instead pull in thousands of feature-tagged tests across the whole tree. The
policy therefore gains a **prefix-scoped** claim: a feature-tagged test is a
candidate only when its path sits under a declared area and _every_ tag it
declares is claimed by that area.

**Produces:** a `featureAreas` key in the policy, an
`Es5CandidateInfo.features` field replacing `hasFeatures`, and
`scanFrontmatter().features`.

- [ ] **Step 1: Write failing tests** in `test/es5-selection.test.js`:
      `scanFrontmatter` returns the flow-sequence feature list, and returns an
      empty list for block-style `features:` while still reporting the tag is
      present; `parseEs5Selection` rejects a `featureAreas` entry with an
      unknown key, an empty/unsorted/duplicated feature list, an unsorted or
      duplicated area list, a prefix outside `test/`, or an empty reason;
      `isCandidatePath` keeps a feature-free test, drops a feature-tagged test
      outside every area, drops one inside an area that declares a tag the
      area does not claim, and keeps one whose every tag the area claims.
- [ ] **Step 2: Run `npm run test:node` and confirm failures.**
- [ ] **Step 3: Implement.** Add `featureAreas` to `POLICY_KEYS` and to the

      `declaresFeatures: boolean` so block-style frontmatter (which the
      textual scanner cannot list) keeps its current "excluded" answer; update
